# PR #45 [中-1] 仕様: 手動切替後の date 基準補正を実際に走らせる

ブランチ `feature/converts-coord-basis/42`、PR #45 レビュー指摘 [中-1] 対応で追加した仕様。本ドキュメントはその振る舞い仕様。実装と整合する。
（動作詳細の更新頻度の高い箇所は `.hermes/rules/coordinate-normalization.md` を参照。）

## 背景・目的

Issue #42 で追加した Web admin の coord_basis 手動切替（topmost → date）は、**template を date 基準へ
シフトするだけ**で、対象 clinic（同日付候補 2 件: 調剤日/発行日）では date 基準の補正が実際には走らなかった。

PR #45 の検証記述「topmost では、抽出 (`*-structured_data.json` に出力) できなかったデータの抽出の成功があった」は
**誤り**である。コード読解と実データ再現の両方で確認した事実:

1. 手動切替後、template は `coord_basis='date'` / date box が原点 `[[0,0],...]` になる
   （`data/verify-01.db` の「なの花薬局札幌二十四軒店」で確認）。
2. 実 raw には date 候補が 2 件（`調剤日：2026/09/02` box `[132,269]..` と `発行日：2026/09/02` box `[127,298]..`）。
   両方とも同じ `2026-09-02` に正規化されるため `find_date_candidates` が 2 件を返す。
3. 旧 `resolve_date_anchor` は `template_basis != "topmost"` のとき即 None を返す
   （date 基準 template の date box は原点で、topmost raw の近接判定が無意味なため）。
   → `apply_date_anchor_normalization` が早期 return し、raw は topmost のまま。
4. `structural_parser._apply_template_corrections` は `coord_basis=='date'` のとき座標ベースのフィールド上書きを
   スキップする（Issue #40 ガード: topmost raw × date template の基底不一致防止）。
   → このクリニックでは座標ベースの抽出が一切走らず、LLM/テキスト抽出フォールバックのみ。

本対応の目的は、**手動切替後も date 基準の補正（座標ベースのフィールド抽出）を実際に走らせ、
`*-structured_data.json` へ反映**すること。PR #45 の主張を「実際に成立する」形にする。

## 用語

| 語 | 定義 |
|----|------|
| date 基準 template | `templates.coord_basis == 'date'`。date box が原点にあり、他フィールドは date box 左上起点の相対座標 |
| レイアウト整合スコアリング | 各 date 候補 box を仮 anchor とし、date 基準 template の date 以外フィールドを「フィールド中心 + 候補 top-left」で実 raw 座標系へ投影して整合度を測る手法 |
| 座標ベース抽出 | `search_fields_by_proximity(entries, coords, threshold)` による、box 近傍テキストでのフィールド値の引き直し |

## 対応方針（確定: Q1=案A）

### Q1: 座標抽出の組み込み先 — 案A（`apply_date_anchor_normalization` 内に内包）

- `apply_date_anchor_normalization(raw_path, structured, db_path, proximity_threshold, output_dir=None)` に
  `output_dir` を追加し、成功時に `_apply_coordinate_extraction()` を内包して呼ぶ。
- `output_dir` が None の呼び出し（`--input-json` 経路・DB 同期確認テスト）は従来どおり structured を変更しない
  （後方互換）。

## 変更 1: `resolve_date_anchor` の date 基準 2 候補解決

`app/date_anchor.py::resolve_date_anchor` に `template_coords`（date 基準の coords_corrections 全体）を追加し、
`template_basis=='date'` かつ候補複数のとき、レイアウト整合スコアリングで一意な候補を選ぶ。

### 選定ロジック

1. 候補 0 件 / date box 未学習 → 従来方式（None）。
2. 候補 1 件 → 採用（basis に依らない。従来どおり）。
3. `template_basis=='topmost'` → 従来の近接 disambiguation（date box 中心から 50px 以内で一意）を維持。
4. `template_basis=='date'` → `_resolve_date_basis_candidate()`:
   - 各候補 box の top-left を仮 anchor とする。
   - date 以外の template フィールド中心を `フィールド中心 + 候補top-left` で raw 座標系へ投影する。
   - 最寄り raw box 中心までの距離を測り、スコア = (50px 外のフィールド数, 距離合計) を計算。
   - 辞書順最小の候補を採用。**同一点数の候補が 2 つ以上 → None（安全側フォールバック）**。
5. それ以外（不一致・曖昧）→ None。

### 閾値

| 項目 | 値 | 出典 |
|------|-----|------|
| レイアウト整合の近接閾値 | 50.0 px | `DEFAULT_PROXIMITY_THRESHOLD` / `resolve_date_anchor` 既定（新規パラメータなし） |

実データ `IMG_20260929_104357-1-raw_data.json` × 手動切替後 template で検証:
調剤日（距離合計 76.0）vs 発行日（113.9）→ 調剤日が一意に選ばれる。

## 変更 2: date 基準再正規化後の座標抽出と structured_data.json 反映

`apply_date_anchor_normalization` が成功（offset を返す）したとき、`output_dir` 指定時のみ:

1. date 基準へ再正規化済み raw を `search_fields_by_proximity` で **date 基準 template coords** と照合。
   - date 基準化済みの coords を使う: topmost から自動移行した場合は `shift_template_to_date_basis()` の結果、
     既に date の場合は template の coords そのまま。
2. 空でない結果を `structured` へ上書き（`date` フィールドは除外。値は座標抽出優先）。
3. `OutputWriter.write()` で `*-structured_data.json` を再出力。
4. **レシートは insert しない**（`insert_receipt` は呼ばない。二重登録防止）。

### #40 ガードとの関係

`_apply_template_corrections()`（前方補正）の時点は raw が topmost のため、`coord_basis=='date'` の
座標ベース上書きは**据え置きでスキップ**（#40 ガード維持）。本対応は「date 基準へ再正規化した後」にのみ
座標抽出を適用するため、topmost raw × date template の基底不一致は変わらず防止される。
