# Issue #47 仕様: date anchor 再正規化・座標抽出の実データ検証ツール

PR #45 [中-1] / PR #46 [中-2] のレビューで指摘された「date 基準テンプレートへ切替後に、実際の raw OCR JSON から
date anchor を解決し、date 基準への再正規化と座標ベース抽出が正しく走るか」を**実データで再現できる**検証ツールの仕様。
本ドキュメントはその振る舞い仕様で、実装と整合する。

## 背景・目的

Issue #39/#42 で導入した `coord_basis='date'`（date 基準）テンプレートの補正経路は、実データ検証の手段が
本番 2 経路（画像 OCR / watcher）を通した確認に限られ、レビュー時に「候補一覧・採用理由・適用オフセット・
再正規化後の座標・抽出結果」を段階ごとに追跡できなかった。本ツールはアプリの**既存ロジックを非複製のまま順に呼び**、
date 基準補正の全段階を確認できる read-only CLI を提供する。本番処理フローは変更しない。

## 用語

| 語 | 定義 |
|----|------|
| date 基準 template | `templates.coord_basis == 'date'`。date box が原点にあり、他フィールドは date box 左上起点の相対座標 |
| 作業用コピー | `--db` / `--raw` を一時領域（`--workdir`）へ複製したもの。ツールは **コピーだけ** を読み書きする |
| 座標ベース抽出 | `search_fields_by_proximity(entries, coords, threshold)` による、box 近傍テキストでのフィールド値取得 |

## 実装: `app/verify_date_anchor.py`（新規 1 モジュールのみ）

### CLI

```
uv run python -m app.verify_date_anchor \
  --raw <raw_data.json> --structured <structured_data.json> --db <db.sqlite3> \
  [--threshold 50.0] [--workdir <dir>] [--report <path>]
```

- `app` は名前空間パッケージ（`__init__.py` なし）のため `-m` 実行可。PaddleOCR 等の重い依存は import しない。
- 引数: `--raw`（date anchor 適用前の topmost 基準 raw JSON）、`--structured`（clinic/date を提供）、
  `--db`（coord_basis='date' テンプレートを含む SQLite）。入力ファイル名は不問（中身のみ判定）。

### 動作フロー（本番 `apply_date_anchor_normalization` と同じ順序・同じ関数を直接呼ぶ）

1. **前提チェック（作業コピー上）**: clinic 名→id を読み取り専用で解決（`get_or_create_clinic` は INSERT するため
   **使わない**）→ `get_latest_template_by_clinic` でテンプレート取得。`coord_basis=='date'` かつ
   `coords['date']` 非 None（date box 学習済み）を確認。1 つでも満たさなければ理由を print し `exit 2`。
2. **段階1 候補検索**: `find_date_candidates(entries, structured_date)`（既存 `parse_date()` による日付正規化比較）。
3. **段階2 候補解決**: `resolve_date_anchor(entries, date, template_date_box=coords['date'],
   template_basis='date', template_coords=coords, proximity_threshold=threshold)`。
   `None`（同点/曖昧）の場合は「解決不能（安全側フォールバック・誤候補は採用しない）」を print し `exit 1`。
4. **段階3 座標再正規化**: `normalize_coordinates_by_anchor(raw_copy, anchor)` — 作業コピーを date 基準に上書きし、
   戻り値の offset を報告。
5. **段階4 座標ベース抽出**: `search_fields_by_proximity(entries_date, coords, threshold=threshold)` —
   date 以外のフィールド値を報告。

### 終了コード

| exit | 意味 | 条件 |
|------|------|------|
| 0 | 検証完了 | anchor 解決 → 再正規化 → 抽出が完了 |
| 1 | 解決不能（同点） | `resolve_date_anchor` が None（安全側フォールバック） |
| 2 | 前提不成立・入力欠落 | template 欠落 / basis != date / date 未学習 / 入力ファイル不在 |

## 非破壊の保証

- `--db`・`--raw` は必ず作業用コピーへ複製し、オリジナルは一切触らない。`--structured` は読み取り専用。
- `process_input_json()` / `insert_receipt` は**呼ばない**（レシート重複登録を防ぐ）。
- 抽出結果は stdout / 任意の `--report` JSON にのみ書き出し、リポジトリ内の既存出力ファイルは書き換えない。

## 閾値・比較（既存を再利用、新規パラメータなし）

- `proximity_threshold` 既定: `app.structural_parser.DEFAULT_PROXIMITY_THRESHOLD`（50.0）。
- 日付比較: `app.normalization.parse_date()`（`find_date_candidates` 内部で使用）。

## サンプル実測（2026-11-02 このブランチで確認）

コマンド:
```bash
uv run python -m app.verify_date_anchor \
  --raw output_json/IMG_20261028_155506_1793242101-raw_data.json \
  --structured output_json/IMG_20261028_155506_1793242101-structured_data.json \
  --db data/verify-01.db
```

実測結果:
- 前提OK（なの花薬局札幌二十四軒店 template は coord_basis='date'）。
- 段階1: date 候補 2 件（`調剤日：2026/10/28` box `[7,295]..` と `発行日：2026/10/28` box `[6,325]..`、
  両方 `2026-10-28` に正規化）。
- 段階2: date 基準レイアウト整合スコアリングで `調剤日` box `[[7,295],[279,306],[278,337],[6,326]]` を採用。
- 段階3: 適用オフセット `(6, 295)`。
- 段階4: 抽出 `name='相原'` / `clinic='なの花薬局札幌二十四軒店'` / `amount='￥1,450'`。
- `exit 0`。実行前後の `sha256sum`（raw / db）は一致（オリジナル不変）。

前提不成立のサンプル（しんかメンタルクリニックは verify-01.db に無い）: `対象テンプレートが見つかりません` で `exit 2`。
