# Issue #51 仕様: coord_basis の整合（Web フォーム修正時に date 基準へ揃えて維持）

Web 管理画面のトグル（topmost → date）適用後、同クリニックのレシートを Web フォームで修正すると、
`templates.coords_corrections` が従前とは異なる基準の座標で上書きされる一方、`templates.coord_basis`
との間に**基底不一致**が生じる問題を解消する仕様。将来の date anchor 補正の強制（Issue #50）の前提となる
座標系整合性を担保する。本ドキュメントは実装と整合する振る舞い仕様。

> **経緯（レビュー P1 を踏まえた方針変更）**: 当初は「修正で `coord_basis` を `topmost` へ戻す（案i）」としていたが、
> レビュー（`.github/reports/pr-52-review.md` [P1]）で「基底だけを切り替えると未修正フィールドが混在し、
> 保存済み OCR が date 基準なら修正フィールド自体も topmost とは限らない」ことが指摘された。
> `topmost` への逆変換はシフト後の絶対位置が失われ一意に決まらないため、**案(ii) に変更**:
> テンプレート全座標を**同一基準（date）に保つ**ため、修正座標を **date 基準へ変換**して
> `coord_basis` は `date` のまま維持する。座標全体と基底を常に一致させる。

## 背景・目的

- 修正座標はレシートの `ocr_json` の座標基準に依存して決まる（`_resolve_coord_results`）。
  `receipts.ocr_json` は date anchor 実行時（`date_anchor.apply_date_anchor_normalization` → acceptance 6）に
  **date 基準で上書き保存**される（`app/date_anchor.py:341-346` / `app/db.py:598-637`）。
- 一方、`coord_basis` が変わらないまま `coords_corrections` を上書きすると、DB 内部で「座標基準」と
  `coord_basis` が食い違う（前方補正が topmost 基準なのに date 扱い等の基底不一致）。
- 対策: Web フォーム修正時、
  - date 基準テンプレートなら**修正座標を date 基準へ変換して書き込み、`coord_basis` は `date` のまま維持**。
  - date anchor 未解決（基準を安全に判別できない）なら**座標を書き込まず、基底も変えない**（安全側フォールバック）。
  - topmost / 未学習テンプレートは従来どおり（基準・座標ともそのまま）。

## 用語

| 語 | 定義 |
|----|------|
| coord_basis | `templates` の座標基準列。`'topmost'`（従来基準） / `'date'`（date 基準） |
| Web フォーム修正 | `PUT /{file_stem}` → `ReceiptUpdater.update_receipt()` → `process_feedback()` の修正経路 |

## 全体フロー（修正経路）

```
PUT /{file_stem}
  -> ReceiptUpdater.update_receipt()
  -> OCRCoordinateService.process_feedback()
     -> _resolve_coord_results()      # レシート ocr_json の基準でフィールド座標を決定
  -> process_correction_feedback() ★変更
     -> 既存 template の coord_basis が 'date' ?
        Yes -> receipt の date box top-left で修正座標を date 基準へ変換して書込む
               （coord_basis は 'date' のまま維持） ※ anchor 未解決なら書込まず維持
        No  -> 従来どおり書込む（coord_basis は topmost/新規既定）
     -> upsert_template(coord_basis=...) ★（INSERT/UPDATE 両ルート対応は既存）
     -> insert_template_history(change_reason='user_correction')
```

- テンプレート管理画面（`GET /admin/templates`）は DB の `coord_basis` を読んで表示するのみ。コード変更は不要で、
  date テンプレを修正しても `topmost` には変わらず `date` 表示のまま。

## 変更の核心

### 1. `db.upsert_template()` の任意引数 `coord_basis: Optional[str] = None`

- 非 None → INSERT/UPDATE の**両方**でその値を設定（SQL の値リストと UPDATE 句に `coord_basis` を含める）。
- None（従来呼び出し）→ 従来どおり `clinic_id / version / coords_corrections` のみ。INSERT はスキーマ既定
  `'topmost'`、UPDATE では列を**変えない**（後方互換）。
- 本仕様では process_correction_feedback が常に `coord_basis` を明示渡し（date なら `'date'`、それ以外は
  `None`/`'topmost'` を維持）。

### 2. `process_correction_feedback()` で date テンプレなら修正座標を date 基準へ変換

```python
existing_basis = (existing or {}).get("coord_basis")
if existing_basis == "date":
    shifted = _shift_correction_to_date_basis(db_path, receipt_id, field_coords_map)
    if shifted is None:
        logger.warning(...)  # anchor 未解決 → 座標を書き込まない
        return {"updated_fields": [], "not_found_fields": not_found_fields, "history_id": None}
    # shifted（date 基準）で上書きし、coord_basis は 'date' のまま
else:
    # 従来どおり field_coords_map をそのまま書き込み、coord_basis は既存/既定
```

**変換の仕組み** (`_shift_correction_to_date_basis`):

- 修正座標の基準 == 修正レシート `ocr_json` の基準。`ocr_json` を取得し、その中から
  `find_date_candidates(ocr_json, structured_date)` で**一意な date box** を特定。
- その date box の top-left で全修正座標を減算（`coord_normalizer.shift_template_coords`）。
  - ocr_json が **topmost 基準**: date box は絶対位置 → 減算で **topmost → date 変換**。
  - ocr_json が **date 基準**（anchor 実行済み）: date box は原点 → 減算は **no-op**。
- 上記により、修正座標の基準が topmost でも date でも、常に date 基準の座標が得られる。

**安全側フォールバック**: 受け取り側の `receipt_id` が無い / `ocr_json` が無い / date text が無い /
date 候補が 0 件 or 複数（曖昧）の場合、基準を安全に判別できないため、**修正座標を書き込まず、
`coord_basis` も変更しない**（date テンプレートを破壊しない。レビュー指摘「基準を安全に判別できない場合は
basis だけを切り替えない」の date 側適用）。テンプレート変更・履歴記録も行わない。

| 既存 basis | 変換可否 | 結果（coord_basis → coords） |
|-----------|----------|------------------------------|
| `None`（新規・未学習） | — | 既定 `topmost`、座標そのまま（従来どおり） |
| `'topmost'` | — | `topmost` のまま、座標そのまま |
| `'date'` | 可 | **`date` のまま、修正座標を date 基準へ変換して書込む** |
| `'date'` | 不可（anchor 未解決） | **`date` のまま、座標は書かない（既存 coords 不変）** |

## なぜ topmost へ戻さないのか（設計判断）

- `topmost` への逆変換（date → topmost）は、テンプレートを date 基準へシフトした際に適用した
  **絶対オフセットが永続化されていない**ため一意に決まらない（`coord_normalizer.shift_template_to_date_basis`
  はシフト後のみを保存する）。過去分の補完も不可。
- 一方 **topmost → date への順変換**は、修正レシート自身の `ocr_json` から date box を特定できるため、
  新規の逆変換基盤やスキーマ変更**不要**で実現できる。
- さらに `ocr_json` が date 基準なら date box は原点なので、同一コードで **no-op** になる（両基準を一括処理）。
- date を「最終基準」とする方向性は Issue #50（date anchor 補正の強制）とも整合。

## DB スキーマ変更

- なし。`templates.coord_basis TEXT NOT NULL DEFAULT 'topmost'` は既存（Issue #39）のまま。
- 補足: `coord_basis` はスキーマ上 `NOT NULL` のため NULL は入らない。コード上の `(existing or {}).get(...)` は
  新規 template（existing が None）の扱いとしての防御であり、DB の NULL を想定したものではない。

## エラーハンドリング

| シナリオ | 対応 |
|---------|------|
| 既存 template なし（新規作成） | `existing_basis=None` → `upsert` は既定 `topmost`（従来どおり） |
| `coord_basis` が不明・旧データ | `(existing or {}).get(...)` が `None` → 既定 topmost のまま。破壊しない |
| date テンプレ + receipt_id 無し / ocr_json 無し | anchor 判定不能 → 座標を書かず基底も変えない（安全側） |
| date テンプレ + date 候補 0 件 or 複数 | anchor 判定不能 → 座標を書かず基底も変えない（安全側） |
| `upsert_template` の UPDATE セットが空 | `coord_basis` 非 None の場合のみ SQL に付与。既存必須カラムの UPDATE は常に維持 |
| low_confidence 等で feedback 自体が止まる | 既存フローが `ReceiptUpdater` 側でゲート。変更なし |
| 座標が全フィールド未検出 | `updated_fields` 空 → 早期 return（既存） |
