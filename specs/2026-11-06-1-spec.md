# Issue #51 仕様: coord_basis の整合（Web フォーム修正後に topmost へ戻す）

Web 管理画面のトグル（topmost → date）適用後、同クリニックのレシートを Web フォームで修正すると、
`templates.coords_corrections` がトグル前（topmost 基準）の座標で上書きされる一方、`templates.coord_basis`
は `date` のまま残る**矛盾**を解消する仕様。将来の date anchor 補正の強制（Issue #50）の前提となる
座標系整合性を担保する。本ドキュメントは実装と整合する振る舞い仕様。

## 背景・目的

- 修正座標はレシートの `ocr_json`（通常 topmost 基準）から決まる（`_resolve_coord_results`）。
- その座標で `templates.coords_corrections` を上書きするが、旧 `upsert_template` の UPDATE は `coord_basis` に触れなかった。
- 結果、`coord_basis='date'` のまま `coords_corrections` が topmost 座標に置き換わり、DB 内部で「座標基準」と
  `coord_basis` が食い違う（前方補正が topmost 基準なのに date 扱いの基底不一致）。
- 対策: Web フォーム修正で topmost 基準座標を書き込むとき、`coord_basis` を `topmost` へ戻して整合させる。

## 用語

| 語 | 定義 |
|----|------|
| coord_basis | `templates` の座標基準列。`'topmost'`（従来基準） / `'date'`（date 基準） |
| Web フォーム修正 | `PUT /{file_stem}` → `ReceiptUpdater.update_receipt()` → `process_feedback()` の修正経路 |

## 全体フロー（修正経路）

```
PUT /{file_stem}
  -> ReceiptUpdater.update_receipt()
  -> OCRCoordinateService.process_feedback()
     -> _resolve_coord_results()      # レシート ocr_json（topmost 基準）からフィールド座標を決定
  -> process_correction_feedback() ★変更
     -> 既存 template の coord_basis が 'date' ? Yes -> 'topmost' へ戻す
     -> upsert_template(coord_basis=...) ★変更（INSERT/UPDATE 両ルート対応）
     -> insert_template_history(change_reason='user_correction')
```

- テンプレート管理画面（`GET /admin/templates`）は DB の `coord_basis` を読んで表示するのみ。コード変更は不要で、
  DB 値が `topmost` に戻れば自動反映。

## 変更の核心

### 1. `db.upsert_template()` に任意引数 `coord_basis: Optional[str] = None` を追加

- `coord_basis` 非 None → INSERT/UPDATE の**両方**でその値を設定（SQL の値リストと UPDATE 句に `coord_basis` を含める）。
- `coord_basis` None（従来呼び出し）→ 従来どおり `clinic_id / version / coords_corrections` のみ。INSERT は
  `coord_basis` 列へ触れずスキーマ既定 `'topmost'` に従い、UPDATE では列を**変えない**（後方互換）。
- 条件分岐で UPDATE 句の SQL 文字列を組み立てる（`coord_basis` None のとき `coord_basis = excluded.coord_basis` を
  含めないことで既存値破壊を防ぐ）。

### 2. `process_correction_feedback()` で既存 basis が `date` なら `topmost` へ戻す

```python
existing_basis = (existing or {}).get("coord_basis")
coord_basis = "topmost" if existing_basis == "date" else existing_basis
upsert_template(..., coord_basis=coord_basis)
```

| 既存 basis | 渡す coord_basis | upsert の結果 |
|-----------|------------------|----------------|
| `None`（新規・未学習） | `None` | スキーマ既定 `topmost`（従来どおり） |
| `'topmost'` | `'topmost'` | `topmost` のまま（変化なし） |
| `'date'` | `'topmost'` | **`topmost` へ戻る（矛盾解消・受入条件1）** |

- 座標が 1 つも見つからなかった場合（`updated_fields` 空）は、history なし・template 変更なしで早期 return（従来どおり）。

## DB スキーマ変更

- なし。`templates.coord_basis TEXT NOT NULL DEFAULT 'topmost'` は既存（Issue #39）のまま。
- 補足: `coord_basis` はスキーマ上 `NOT NULL` のため NULL は入らない。コード上の `(existing or {}).get(...)` は
  新規 template（existing が None）の扱いとしての防御であり、DB の NULL を想定したものではない。

## 設計判断と根拠

| 項目 | 決定 | 根拠 |
|------|------|------|
| 修正時の基準 | Web 修正は**レシート ocr_json 基準（実質 topmost）**に依拠 | 修正座標は `_resolve_coord_results` がレシート由来で決める。date anchor が機能しない現状では topmost が実勢 |
| coord_basis の扱い | 既存が `date` のとき**上書きで `topmost` へ戻す** | 書き込む座標の実基準に整合。片方向トグルを「修正時のみ実質解除」 |
| 代替案 | 案B（修正座標の基準を ocr_json から都度判定）は不採用 | ocr_json に基準フラグが無く複雑。案C（常に topmost 強制）は date 基準レシート修正ケースを壊す恐れ |
| `upsert_template` | 任意引数 `coord_basis`（未指定なら現状維持） | 呼び出し元を壊さず疎結合。INSERT/UPDATE 両ルートで整合 |
| 履歴 | 既存 `insert_template_history`（`change_reason='user_correction'`）を利用 | 新規 SQL を増やさない。トグル時（`manual_basis_toggle`）と別 reason は false になるため既定のまま |
| 管理画面 | 変更不要 | `list_templates` が DB の `coord_basis` を読み表示するだけ → 受入条件2 は DB 値修正で自動満たす |

## エラーハンドリング

| シナリオ | 対応 |
|---------|------|
| 既存 template なし（新規作成） | `existing_basis=None` → `upsert` は既定 `topmost`（従来どおり） |
| `coord_basis` が不明・旧データ | `(existing or {}).get(...)` が `None` → 既定 topmost のまま。破壊しない |
| `upsert_template` の UPDATE セットが空 | `coord_basis` 非 None の場合のみ SQL に付与。既存必須カラムの UPDATE は常に維持 |
| low_confidence 等で feedback 自体が止まる | 既存フローが `ReceiptUpdater` 側でゲート。変更なし |
| 座標が全フィールド未検出 | `updated_fields` 空 → 早期 return（history / template 変更なし） |
